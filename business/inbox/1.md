## Частина 1. Бізнес-конспект (Executive Summary)

### 1. Концепція та мета проєкту
* **Проблема челенджу NASA:** На Місяці, Марсі та в інших місцях космосу залишилося багато обладнання та артефактів, які вийшли з експлуатації, але мають величезну наукову та історичну цінність. Потрібно створити захоплюючий освітній інструмент для школярів та любителів космосу, який розповість історію цих об'єктів.
* **Відхилені/базові ідеї:** Звичайний вебсайт-каталог або просто інтерактивна 3D/2D карта — це занадто банально і нудно для сучасного користувача (туди ніхто не буде регулярно заходити, а 3D-фреймворки погано сумісні зі специфічними координатами NASA).
* **Головна ідея («Фабрика контенту»):** Замість того, щоб змушувати людей шукати сайт, потрібно йти туди, де вже сидить аудиторія (TikTok, YouTube Shorts, Instagram Reels, Telegram, Threads, Reddit, подкасти). Проєкт являє собою **автоматизовану ШІ-фабрику контенту** та екосистему навколо бази даних NASA.
* **Суть рішення:** 
  1. Система парсить офіційні ресурси NASA (постійно оновлюючи дані) і зберігає їх у структуровану базу даних.
  2. Надається **MCP-сервер (Model Context Protocol)**, який дозволяє будь-яким зовнішнім ШІ-агентам (наприклад, Claude, Gemini) підключатися до нашої бази і брати перевірені факти NASA без «галюцинацій» та вигадок.
  3. Створюється **Десктопний застосунок («Фабрика контенту»)** для креаторів (або автономних ШІ-агентів), який у два кліки генерує вертикальні відео (Shorts/TikTok), пости та аудіоподкасти на основі шаблонів і реальних даних NASA, та публікує їх через API соцмереж.
  4. Створюється **Вебсайт-портал** з інтерактивною картою, фільтрами та згенерованими ШІ-подкастами, куди веде трафік із соцмереж.

### 2. Архітектура системи (Схема C4 та Стек технологій)
* **Джерела даних (Зовнішні):** Офіційні ресурси та API NASA (5–6 різних джерел).
* **Бекенд та База даних:**
  * **Фреймворк:** Python + **Django** (обрано замість FastAPI через наявність готової адмінки з коробки, що критично для економії часу на хакатоні) + **Pydantic** (для валідації DTO).
  * **Завантажувач (Парсер):** Сервіс на Django, який щогодини опитує ресурси NASA, обробляє дані та кладе в БД.
  * **Два власних API:** Перше — під вебсайт-портал, друге — під десктопний редактор («Фабрику контенту»).
  * **MCP-сервер:** Шлюз для нейромереж та ШІ-агентів для прямого доступу до бази даних (приклад домену: `lihtar.org`).
* **Клієнтські застосунки (Фронтенд):**
  * **Десктопний додаток («Фабрика контенту»):** Нативний застосунок на **Tauri** або **Electron** (TypeScript + UI-бібліотека **Chakra UI**). Має локальний доступ до файлової системи для збереження та монтажу відео, накладання ефектів та української/англійської ШІ-озвучки.
  * **Вебсайт-портал:** Сайт із картками артефактів, інтерактивною картою, панорамами, аудіоподкастами (можлива генерація через Google NotebookLM) та посиланнями на згенеровані Shorts.
* **Зовнішні інтеграції публікації:** YouTube Data API (підтримує завантаження відео до 256 ГБ з коду), TikTok API (потребує вивчення лімітів/платності), Telegram, Threads.
* **План «Супер-Максимум» (Джекпот для журі):** Написати локальний CLI/MCP інтерфейс для самої «Фабрики контенту», щоб локальний ШІ-робот на комп'ютері міг сам керувати фабрикою і штампувати ТікТоки без участі людини.

### 3. Інструменти розробки та процеси (Workflow)
* **ШІ-оркестрація:** Використання **Orca** для паралельного запуску ШІ-агентів (поки один агент пише код в одній гілці, розробник контролює іншого).
* **ШІ-агенти та IDE:** Використання **Antigravity**, Claude Code, OpenCode, Grok, Copilot.
  * *Важливі налаштування безпеки в Antigravity:* Вимкнути телеметрію (`Telemetry: Off`), увімкнути запит дозволу на виконання тулзів (`Ask/Always review`), щоб агент випадково не видалив файли на ПК і не списав зайві кошти. Використання гарячих клавіш `F5`/`F6` для голосового диктування промптів.
* **Дизайн через ШІ:** Розширення **Pencil** (файли `.pen`) у зв'язці з Antigravity та MCP від Figma для швидкої генерації UI-макетів.
* **Git-флоу:** Робота виключно через окремі гілки під кожну задачу (`feature/назва-задачі` або за ролями) та злиття через **Pull Requests (PR)** у `main`/`develop`, щоб уникнути конфліктів коду.
* **Оптимізація бізнес-процесів (Домашнє завдання команді):** Кожен учасник має пройтися по надісланій дорожній карті (Roadmap) та написати власні скіли (правила в папці `.agents` / skills) для ШІ, які автоматизують його рутинну роботу.
