# Стандарт Версіонування Специфікацій (spec_versioning.md)

Цей регламент визначає **Best Practices** управління версіями продуктової, бізнес- та технічної специфікації.

---

## 1. Схема версіонування: SemVer 2.0.0 для специфікацій

Формат версії: **`vMAJOR.MINOR.PATCH`**

### `MAJOR` (Мажорна версія: vX.0.0)
Інкрементується при фундаментальних/ламаючих змінах (Breaking Changes):
* Кардинальна зміна бізнес-моделі або цільової аудиторії продукту.
* Зміна або видалення існуючих сутностей `ENT-*`, ключових полів `FIELD-*` чи операцій `OP-*`, що ламає зворотну сумісність клієнта й сервера.
* Зміна архітектурної парадигми (наприклад, моноліт $\to$ мікросервіси/Event-Driven).

### `MINOR` (Мінорна версія: v1.X.0)
Інкрементується при зворотно-сумісному розширенні специфікації:
* Додавання нових фіч `FEAT-*`, нових сутностей `ENT-*` або операцій `OP-*`.
* Додавання нових ролей `ROLE-*` чи розширення роадмапу.
* Додавання нових досліджень ринку чи розділів глосарію `TERM-*`.

### `PATCH` (Патч-версія: v1.0.X)
Інкрементується при точкових уточненнях та виправленнях без зміни структури:
* Уточнення валідацій полів (`FIELD-*`), описів помилок або прекондишнів.
* Виправлення описок, термінологічних неточностей, оновлення діаграм.
* Переведення елементів зі статусу `[AI-DRAFT]` у затверджені після рев'ю.

---

## 2. Життєвий цикл статусу версії (Specification Lifecycle)

Кожна версія специфікації знаходиться в одному з офіційних станів:

```
[DRAFT]  --->  [IN_REVIEW]  --->  [APPROVED]  --->  [SUPERSEDED]
   |                |
   v                v
[REJECTED]      [CHANGES_REQUESTED]
```

1. **`DRAFT` (Чернетка)**: Специфікація формується, містить незаповнені розділи та блоки `[AI-DRAFT]`.
2. **`IN_REVIEW` (На рецензуванні)**: Специфікація заморожена для внесення суттєвих змін, проходить перевірку аналітиками, техлідом або бізнесом.
3. **`APPROVED` (Затверджена)**: Єдине джерело істини для поточної розробки. Команда розробки бере задачі в спринт виключно з затвердженої версії.
4. **`SUPERSEDED` / `DEPRECATED` (Застаріла)**: Замінена новішою мажорною/мінорною версією.

---

## 3. Обов'язкова структура аудит-логу (`00_VERSION.md`)

Файл `00_VERSION.md` розташовується в корені специфікації та повинен містити:
1. **Зведену таблицю поточного статусу**:
   - Номер поточної версії (`vX.Y.Z`).
   - Статус життєвого циклу (`APPROVED`, `IN_REVIEW`, `DRAFT`).
   - Дата останньої модифікації.
   - Відповідальний власник (Owner / Lead Analyst).
   - Метрики покриття (кількість фіч, сутностей, діаграм).
2. **Хронологічний журнал змін (Changelog)** у зворотному порядку:
   - Розділи: `Додано (Added)`, `Змінено (Changed)`, `Виправлено (Fixed)`, `Видалено (Removed)`.
   - Посилання на конкретні ID об'єктів (`FEAT-*`, `ENT-*`, `OP-*`).
